# VERTO Web — проєктний документ

> Спільний переклад ігрових локалізацій (`.locres` Unreal Engine, `.csv`, `.txt` і `.json`) з акаунтами, ролями, статусами рядків і прогресом у реальному часі.
>
> Документ описує **фактичний стан** репозиторію `pasherlife/verto` (гілка `main`, коміт `acab0be` і новіші). Усі етапи початкового плану виконано; відхилення від плану та те, що лишилося, — у §9 і §10.

## 1. Короткий опис

| | |
|---|---|
| Тип | Вебзастосунок (SPA + REST API), один процес Node.js |
| Мова інтерфейсу | Українська |
| Бекенд | Node.js **≥ 22.13**, вбудований `node:http`, `node:sqlite`; **без npm-залежностей** |
| Фронтенд | Vanilla JS (ES-модулі), без збірки, `public/` |
| Сховище | SQLite (WAL), файл `data/uelt.db` (змінна `UELT_DB`) |
| Реальний час | Опитування `GET /api/files/:id/changes?since=<rev>` (він же heartbeat присутності) |
| Розгортання | Docker + Caddy (авто-HTTPS) або systemd + nginx/Caddy |
| Тести | `node --test`, **84 тести, усі проходять**; інтерфейс додатково перевірено в Chromium для всіх семи ролей |

**Що вміє система**

- Сім ролей: власник, адмін, менеджер, перекладач, редактор, рецензент, спостерігач (§3).
- Файли проєкту завантажуються як `.locres`, `.csv`, `.txt` (`ключ=текст`) і `.json` (CSV/TXT: автовизначення роздільника й кодування).
- Файл проєкту скачується як `.locres`, `.csv`, `.txt`, `.json`; переклад імпортується з `.locres`, `.csv`, `.txt`, `.json` (§4).
- Статуси рядків («Без статусу» → «На вичитку» → «Затверджено»), статистика слів і рядків, смуга прогресу, присутність, журнал правок.
- Шифрований LUT Code Vein 2, оновлення оригіналу зі звітом, сповіщення на пошту.

**Поняття «портал»** = один розгорнутий екземпляр VERTO Web (одна БД, один домен). Мульти-портальність (кілька незалежних просторів в одній БД) **не реалізована** (§10, питання 1).

### 2.1. Модель даних (SQLite)

| Таблиця | Ключове |
|---|---|
| `users` | `role` (`owner`\|`admin`\|`user`), `is_admin` (синхронізується: owner/admin = 1), `disabled`, контакти (`email`, `discord`, `telegram`) |
| `sessions` | хеш токена, `expires_at` |
| `settings` | `registration` (вільна реєстрація) |
| `projects` | `archived`, `description` |
| `project_members` | `role` (`manager`\|`translator`\|`editor`\|`reviewer`\|`observer`), `can_approve` (синхронізується з роллю) |
| `files` | `format` (`locres`\|`csv`\|`txt`\|`json`), `meta` (JSON: простори імен, `cv2`, `csv: {delimiter, encoding, columns}` / `txt: {separator, encoding, header}` / `json: {shape, encoding, columns}`), `version`, `rev`, `struct_rev` |
| `file_access` | призначення файлів (діє лише для ролі «перекладач») |
| `rows` | `row_key` (`Namespace::Key`), `source`, `translation`, `status`, `ver`, `rev`, пошукові `*_lc` |
| `edits` | журнал правок (стара/нова версія тексту й статусу, автор, час) |

Правила:
- ID рядка — `Namespace::Key`; дублікати отримують суфікс `[n]` (`assignRowIds`).
- Статуси: `0` — без статусу, `1` — на вичитку, `2` — затверджено.
- `rows.ver` — оптимістичне блокування (409 при конфлікті), `rows.rev`/`files.rev` — для поллінгу змін.
- У `rows` службові переноси зберігаються маркерами `<lf>`, `<cr>`, `<cf>`, `<tb>`.
- Усі зміни перекладу пишуться в `edits`.
- Міграції виконуються при відкритті БД (`openDb`), ідемпотентні.

## 3. Ролі та права

Дві області: **портал** (`users.role`) і **проєкт** (`project_members.role`). Єдина таблиця прав — `src/roles.js`; маршрути не порівнюють ролі напряму, а питають `can(...)` / `requireCan` / `requireProjectCan` / `requireFileCan`.

### 3.1. Ролі

| Роль | Область | Суть |
|---|---|---|
| **Власник** (`owner`) | портал | Єдиний, повний доступ до порталу. Налаштування, призначення адмінів, передача власності. Його не можна понизити, вимкнути чи видалити. |
| **Адмін** (`admin`) | портал | Створює проєкти й керує ними, бачить усі проєкти без членства, керує звичайними користувачами. Не чіпає власника й інших адмінів. |
| **Менеджер** (`manager`) | проєкт | Керує призначеним проєктом: учасники й ролі (крім менеджерів), доступ до файлів, завантаження, експорт, оновлення оригіналу, очищення, видалення файлів, журнал активності. |
| **Перекладач** (`translator`) | проєкт | Перекладає **призначені** файли (галочки `file_access`). Результат → «На вичитку». |
| **Редактор** (`editor`) | проєкт | Править переклад у **всіх** файлах проєкту. Не затверджує. |
| **Рецензент** (`reviewer`) | проєкт | Править і **затверджує** рядки в усіх файлах проєкту. |
| **Спостерігач** (`observer`) | проєкт | Лише перегляд файлів, рядків, статистики й присутності. |

Звичайні користувачі порталу мають `users.role = 'user'` і отримують можливості лише через членство в проєктах. Власник і адміни **не додаються** в учасники (API відповідає 400): вони бачать усе й так.

Загальні правила:
- **Архівний проєкт** — лише читання для всіх ролей, включно з власником (запис: завантаження, оновлення, очищення, імпорт, редагування, затвердження). Заблокована дія повертає **409** «Проєкт архівований», якщо без архіву вона була б дозволена; експорт і перегляд працюють. Розархівувати може лише власник/адмін.
- Не-рецензент, який змінив затверджений рядок, скидає його у «На вичитку» (логіка `nextState`).
- Сторонній (не учасник) отримує **404**, а не 403, на будь-яку дію з проєктом чи файлом — існування не розкривається. Учасник без потрібного права — **403**.
- Завжди рівно **один власник** (перевіряється тестом) і щонайменше один активний адмін-або-власник.

### 3.3. Реалізація

- **Портал:** `users.role`; `users.is_admin` лишено й синхронізовано (`owner|admin` = 1), щоб відкат на попередню версію працював.
- **Проєкт:** `project_members.role`; `can_approve` лишено й синхронізовано (`reviewer`/`manager` = 1).
- **Міграція** (одноразова, ідемпотентна, за відсутністю стовпця): найстаріший `is_admin = 1` → `owner`; інші `is_admin = 1` → `admin`; решта → `user`; `can_approve = 1` → `reviewer`, інакше `translator`.
- **`projectAccess`** повертає ефективну роль, `can(cap, {assigned})` з урахуванням архіву, прапорці; **`fileAccess`** додає `canEdit`, `canApprove`, `canImport`, `can(cap)`.
- API учасників приймає `role` (перевіряється) і, для сумісності, старий `canApprove` (→ `translator`/`reviewer`).
- **Передача власності:** `POST /api/admin/transfer-ownership {userId, password}` — лише власник; новий власник має бути активним; колишній стає адміном; сесії обох завершуються; на пошту йде сповіщення.
- **CLI:** `npm run make-admin -- <нік>` (власника не понижує), `node src/cli.js make-owner <нік>` (аварійне відновлення: попередній власник стає адміном).
- **Інтерфейс** ховає недоступні кнопки за правами, які сервер віддає в `me.caps` (проєкт), `perms` (файл) і `role` (сесія); сервер усе одно перевіряє кожен запит.

## 4. Файли проєкту: формати

Файл проєкту — набір **рядків** (`rows`) з оригіналом і перекладом. Джерелом може бути `.locres`, `.csv`, `.txt` або `.json` (`files.format`).

### 4.1. Завантаження в проєкт

Хто: власник, адмін, менеджер. Формат — за розширенням (регістр не важливий).

`POST /api/projects/:id/files?name=<шлях>.locres|.csv|.txt|.json[&cv2=release|demo][&delimiter=…][&safe=1]` — тіло: **сирі байти** файлу. Ліміти: `.locres` 256 МБ, `.csv`/`.txt`/`.json` 20 МБ. `cv2` — лише для `.locres`.

**CSV-джерело** (key + source, за бажанням translation і status):

| Стовпець | Обов'язковий | Синоніми заголовка |
|---|:-:|---|
| `key` | так | `id`, `rowkey`, `ключ`, `ключрядка` |
| `source` | так | `original`, `text`, `оригінал`, `текст`, `джерело` |
| `translation` | ні | `translated`, `переклад`, `перекладенийтекст` |
| `status` | ні | `статус`; значення `0/1/2` або `none/review/approved` (`без статусу`, `на вичитку`, `затверджено`) |

Правила розбору:
- Заголовок зіставляється без урахування регістру, пробілів, `_` і `-`.
- Порожній `key` → помилка з номером рядка; дубль ключа → помилка; різна кількість стовпців у рядку → помилка; невідомий статус → помилка; текст понад 50 000 символів → помилка.
- Порожній `source` дозволений (рядок лишається, 0 слів).
- Справжні переноси рядків у полях перетворюються на маркери `<lf>` і т. д. (обернено — при збиранні `.locres`).
- Переклад, що **збігається з оригіналом**, вважається відсутнім (статус «Без статусу»).
- Непорожній переклад отримує «На вичитку»; значення `status` береться лише з правом затверджувати (завантажувач джерела — власник/адмін/менеджер — його має), `0` ігнорується.
- `files.meta.csv = { delimiter, encoding, columns }`.

**ID → простір імен і ключ** (`csvToLoc`): розбиття за **першим** `::`; без `::` — порожній простір імен. Суфікс `[n]` вважається маркером дубліката лише тоді, коли `n` дорівнює кількості попередніх рядків із тим самим простором імен і ключем (так само нумерує `assignRowIds`); інакше це частина ключа. Після розбору ID перераховуються через `assignRowIds` і мають збігатися з вхідними, інакше — помилка «некоректний формат» (так перевіряється коректність кругового проходу).

### 4.1a. TXT- і JSON-джерела
- **TXT:** `ключ<роздільник>текст` у рядку; роздільник авто (`=`, табуляція, `|`, `;`) або вручну; коментарі `#`/`//` і порожні рядки пропускаються; необов'язковий заголовок `key=source`; escape `\n \r \t \\`. Для `=` пробіли навколо обрізаються. Кодування як у CSV.
- **JSON:** об'єкт (плоский → `object`, вкладений → `nested`, ID = шлях через `::`) або масив записів (`records`: `key`, `source`, необов'язково `translation`, `status`). Нерядкові значення, масиви всередині об'єкта, дублікати ключів — 400 із указанням шляху.
- Усе зводиться до тієї ж моделі (`sourceToLoc`), тож редактор, статуси, оновлення оригіналу й експорт у `.locres` (хеші CRC32, версії 0–2) працюють однаково для csv/txt/json. Експорт у власний формат не зберігає форму вкладеності JSON: `nested` експортується як плоскі ID (`menu::play`); при імпорті назад ID збігаються.

### 4.2. Автовизначення роздільника й кодування CSV

- **Роздільник** (`detectDelimiter`): кандидати `;` `,` табуляція `|` (порядок = пріоритет при нічиї). Для кожного розбираються перші 20 записів з урахуванням лапок; оцінка = (кількість розпізнаних назв стовпців у заголовку) × 1000 + (стабільна кількість стовпців) × 100 + кількість стовпців. Кандидат з одним стовпцем не підходить; якщо жоден не підійшов — помилка з підказкою вказати роздільник вручну. Параметр `delimiter` (`auto`, `comma`, `semicolon`, `tab`, `pipe`) перевизначає автовиявлення; помилковий ручний вибір дає помилку, а не псує дані.
- **Кодування** (`decodeCsv`): BOM UTF-8 → UTF-8; BOM UTF-16 LE/BE → UTF-16; без BOM — строгий UTF-8, інакше **windows-1251**. Файл надходить байтами; результат (`encoding`, `delimiter`) повертається клієнту й показується в діалозі.

### 4.3. Скачування файлу проєкту

Хто: власник, адмін, менеджер. `GET /api/files/:id/export?format=locres|csv|txt|json…` (за замовчуванням — формат джерела).

| Параметр | Значення | За замовчуванням |
|---|---|---|
| `format` | `locres` \| `csv` \| `txt` \| `json` | формат джерела |
| `delimiter` (txt) | `equals` \| `tab` \| `pipe` \| `semicolon` | `equals` |
| `column` (txt) | `translation` \| `source` | `translation` |
| `shape` (json) | `records` \| `object` | `records` |
| `scope` (csv, txt, json) | `all` \| `untranslated` \| `review` \| `approved` \| `notapproved` \| `changed` | `all` |
| `delimiter` (csv) | `semicolon` \| `comma` \| `tab` | `semicolon` |
| `bom` (csv) | `1` \| `0` | `1` (Excel коректно відкриває UTF-8) |
| `safe` (csv) | `1` | вимкнено |
| `version` (locres із CSV-джерела) | `0` \| `1` \| `2` | `2` (Optimized) |

- **`.csv`:** стовпці `key,source,translation,status`; UTF-8, CRLF; маркери `<lf>` тощо виводяться **як є**, тож експорт імпортується назад без змін (перевірено тестом: круговий прохід = 0 змін). `safe=1` ставить апостроф перед клітинками, що починаються з `= + - @`/табуляції (захист від формул Excel); при імпорті такого файлу вмикається `safe` (прапорець у діалозі), і апостроф знімається.
- **`.locres` з `.locres`-джерела:** як раніше — оригінальні версія, хеші, порядок; порожній переклад → береться оригінал; для CV2 — повторне шифрування. Параметр `version` відхиляється (400).
- **`.locres` з CSV-джерела:** хеші обчислюються `strCrc32` (простір імен, ключ, **оригінальний** текст), версії 0/1/2; **версії з CityHash64 (3, 4) відхиляються** (400) — CityHash64 не реалізовано. Значення = переклад, а за його відсутності — оригінал.

### 4.4. Імпорт перекладу

Хто: власник, адмін, менеджер, редактор, рецензент; перекладач — лише призначений файл; спостерігач — ні.

**Один пункт меню** «Імпортувати переклад (.locres / .csv)…» (сторінка проєкту й редактор); обробник за розширенням, незалежно від формату джерела файлу (`.csv` можна імпортувати у файл із `.locres`-джерела й навпаки — зіставлення за ключем).

| Крок | `.locres` | `.csv` |
|---|---|---|
| Перегляд | `POST /api/files/:id/translations` (без `apply`) — звіт | `POST /api/files/:id/csv-preview` — таблиця з діями для кожного рядка |
| Застосування | `…/translations?apply=1&overwrite=0\|1&approve=0\|1` | `POST /api/files/:id/csv-import` з `actions` |

Тіло запитів: JSON `{ csvBase64, format (csv|txt|json), delimiter, safe, actions }` (сирі байти в base64; старе поле `csv` — готовий текст — підтримується для сумісності).

Спільні правила:
- Збіг за ключем `Namespace::Key`; невідомі ключі пропускаються й рахуються.
- Порожній переклад, рівний оригіналу чи поточному — пропускається.
- Нові переклади → «На вичитку»; перезапис наявних — лише явно (`overwrite`/дія `replace`).
- Затверджені рядки змінює лише той, хто має право затверджувати.
- CSV із колонкою `status`: значення `1`/`2` береться лише від того, хто затверджує; `0` ігнорується.
- Кожна зміна пишеться в `edits`; рядок, що змінився між переглядом і застосуванням, дає 409.

### 4.5. Оновлення оригіналу

Хто: власник, адмін, менеджер. `POST /api/files/:id/update[?apply=1][&delimiter=…][&safe=1]`. Для `.locres`-файлу приймає `.locres`, для csv/txt/json-файлу — файл того ж формату (`key`+`source`; `translation`/`status` ігноруються). Рядки зіставляються за `Namespace::Key`: переклади зберігаються; у рядків зі зміненим оригіналом статус стає «На вичитку»; нові додаються; зниклі видаляються разом з перекладом. Спершу звіт, потім застосування.

## 10. Відкриті питання (потребують рішення замовника)

1. **«Портал» = один екземпляр чи кілька?** Поточна реалізація — один портал на встановлення. Кілька незалежних порталів в одній БД (мульти-тенантність із власником у кожного) — окремий, значно більший етап (`portal_id` у всіх таблицях).
2. **Хто скачує:** зараз `owner/admin/manager`. Чи дозволити рецензенту (для перевірки в грі)? Можна винести в налаштування проєкту.
3. **Редактор vs перекладач:** розрізнення за **областю** (усі файли / призначені). Якщо потрібне інше — уточнити.
4. **Рецензент і правка тексту:** зараз може правити; якщо лише затверджувати/повертати — спростити матрицю.
5. **Версія `.locres` для CSV-джерела:** за замовчуванням `Optimized` (2). Чи відомо, яку версію очікує гра/рушій? Збирання не перевірялося в самій грі.
6. **Журнал ролей** (§9): чи потрібен запис змін ролей і передачі власності в журнал активності?

## Знайти й замінити
`POST /api/files/:id/replace` (право редагувати файл; архівний проєкт — лише читання). Тіло: `{ find, replace, matchCase, wholeWord, scope: 'all'|'filter', filter, q, includeApproved, apply }`. Без `apply` повертає лише перегляд (`rows`, `occurrences`, `skippedApproved`, `tooLong`, `samples`). Змінюється лише переклад, оригінал — ні. Пошук буквальний (без регулярних виразів, щоб не наражати сервер на повільні шаблони), `$` у заміні — звичайний символ. Затверджені рядки пропускаються; рецензент може ввімкнути `includeApproved` — тоді вони стають «На вичитку». Кожна зміна пишеться в журнал правок, змінений рядок отримує нову ревізію (поллінг оновить інших редакторів). Інтерфейс: меню «Дії з файлом» → «Знайти й замінити…».
